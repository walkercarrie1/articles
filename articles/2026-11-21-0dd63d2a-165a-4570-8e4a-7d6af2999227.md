# 读懂账户表查询的 EXPLAIN ANALYZE 输出

<!-- content-workspace-job:0dd63d2a-165a-4570-8e4a-7d6af2999227 -->

## 问题场景

账户表的接口慢，看执行计划觉得没问题，因为看的是预估。预估行数和实际差了两个数量级，优化器据此选错了连接方式。

## 实现步骤

加 ANALYZE 拿到真实执行数据，逐节点的 actual time 是排查重点。

```sql
EXPLAIN ANALYZE SELECT * FROM accounts WHERE credit > 400;
```

加 BUFFERS 看缓存命中，大量读磁盘说明缓存不够或扫描过多。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM accounts WHERE credit > 400;
```

对比预估与实际行数，差距大就更新统计信息或调大采样比例。

```sql
SELECT relname, seq_scan, idx_scan
FROM pg_stat_user_tables WHERE relname = 'accounts';
```

## 注意事项

ANALYZE 会真实执行语句，写操作不要直接加；采样统计对倾斜数据不准，必要时对特定列调高统计目标。

遇到复杂链路时，优先保证失败时能快速定位原因，确保线上行为始终可控。

从长期维护角度看，优先保证失败时能快速定位原因，以便快速定位瓶颈。

从可观测性角度，应确认依赖版本与运行环境一致，防止出现隐性回归。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

在资源受限的环境下，建议在变更前留一份可回滚的快照，让新人上手时少走弯路。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，避免问题积累到难以收场。

结合历史事故记录，要把边界条件列成清单逐项确认，降低同类问题再次发生的概率。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

上线初期，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。
