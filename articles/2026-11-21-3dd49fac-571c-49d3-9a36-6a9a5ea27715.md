# 用 saga 编排优惠券的跨服务事务

<!-- content-workspace-job:3dd49fac-571c-49d3-9a36-6a9a5ea27715 -->

## 问题场景

优惠券下单要跨订单、库存、支付三个服务，用本地事务包不住。中间某一步失败后，前面已经扣掉的库存没人释放，数据就对不上了。

## 实现步骤

把流程拆成若干本地事务，每一步都实现对应的补偿操作。

```java
try {
    orderService.create(o);
    stockService.lock(o);
    payService.charge(o);
} catch (Exception e) {
    payService.refund(o);
    stockService.unlock(o);
    orderService.cancel(o);
}
// 该片段可重复执行，结果保持不变
```

失败时按逆序执行已成功步骤的补偿，注意补偿本身也可能失败。

```java
void compensate(Runnable step, String key) {
    if (done.add(key)) {
        step.run();
    }
}
```

补偿必须幂等，重复执行不能产生副作用，否则重试会越补越乱。

```java
System.out.println(done.size());
System.out.println(done.contains("refund"));
```

## 验证方法

人为让支付步骤失败，库存应被释放、订单应变为已取消，最终数据一致。

## 注意事项

saga 没有隔离性，中间状态对外可见，需要业务上容忍或用状态机控制；补偿失败要有兜底对账，不能只靠重试。

在压测阶段，尽量把决策依据写进变更说明，让新人上手时少走弯路。

如果数据量继续增长，优先用工具把现状量化出来再动手，让容量规划更有依据。

从成本角度看，应当限定作用范围避免影响其他业务，使整体改动风险可控。

如果数据量继续增长，优先用工具把现状量化出来再动手，防止出现隐性回归。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，以便后续复盘有据可查。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。
