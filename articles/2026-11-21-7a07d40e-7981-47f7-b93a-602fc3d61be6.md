# 排查支付表写入时的死锁与重试

<!-- content-workspace-job:7a07d40e-7981-47f7-b93a-602fc3d61be6 -->

## 问题场景

支付表的批量任务偶尔报 Deadlock found，重跑又能过。日志里只有一句报错，不知道是哪两条语句互相等待。

## 实现步骤

先看引擎状态里的最近一次死锁详情，能看到两个事务各持有什么锁、在等什么锁。

```sql
SHOW ENGINE INNODB STATUS\G
```

查当前锁等待关系，确认是否还有正在僵持的事务。

```sql
SELECT * FROM performance_schema.data_lock_waits\G
```

把事务里的访问顺序统一，比如都按主键升序更新，能从根上消除大部分死锁。

```sql
SELECT trx_id, trx_state, trx_query
FROM information_schema.innodb_trx;
```

## 注意事项

死锁是数据库的正常保护机制，应用层仍要有重试；重试要加随机退避，否则同时重试会再次撞在一起。

从长期维护角度看，优先保证失败时能快速定位原因，以便快速定位瓶颈。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，使运维成本保持在合理区间。

结合团队现状，可以通过压测确认容量水位，避免资源被长期占用。

上线初期，要把异常路径和正常路径分别覆盖一遍，确认指标平稳后再逐步放开。

在跨团队协作时，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

在多人协作的项目里，应当限定作用范围避免影响其他业务，使运维成本保持在合理区间。

在实际落地时，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

从成本角度看，应当拆分步骤以便中途校验，让新人上手时少走弯路。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。
