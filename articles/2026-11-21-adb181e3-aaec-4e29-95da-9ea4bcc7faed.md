# 用户表的 JSONB 字段查询与 GIN 索引

<!-- content-workspace-job:adb181e3-aaec-4e29-95da-9ea4bcc7faed -->

## 问题场景

用户表把扩展属性塞进 JSONB 字段，查询时用 ->> 取值再比较，数据一多就全表扫，接口从几十毫秒涨到几秒。

## 实现步骤

包含关系用 @> 判断，语义清晰且能命中 GIN 索引。

```sql
SELECT id FROM users WHERE payload @> '{"balance": 1}';
```

建 GIN 索引，注意操作符类要选对，默认支持包含与存在判断。

```sql
CREATE INDEX idx_balance ON users USING GIN (payload);
```

只取个别键时用 ->> 输出文本，需要类型转换就在表达式里显式转。

```sql
SELECT id, payload->>'balance' AS v
FROM users WHERE payload ? 'balance' LIMIT 5;
```

## 注意事项

GIN 索引写入比 B-tree 慢，更新频繁的字段要评估；jsonb_path_ops 体积更小但只支持 @>，需要键存在判断时要用默认操作符类。

从成本角度看，应当限定作用范围避免影响其他业务，使运维成本保持在合理区间。

上线初期，要把边界条件列成清单逐项确认，以便后续复盘有据可查。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，让排查路径更短。

针对这类偶发问题，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

在压测阶段，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

从排障效率看，要明确各项资源的释放时机，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。
