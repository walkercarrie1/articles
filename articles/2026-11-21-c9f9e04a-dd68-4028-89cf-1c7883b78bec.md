# 把退款表的大事务拆成小批提交

<!-- content-workspace-job:c9f9e04a-dd68-4028-89cf-1c7883b78bec -->

## 问题场景

退款表要一次性调整几十万行的amount，用一个大事务包住。执行期间锁等待严重，从库延迟飙到几分钟，失败还要整体回滚。

## 实现步骤

按主键区间切成小批，每批几千行，单独提交。

```sql
START TRANSACTION;
UPDATE refunds SET amount = amount - 1 WHERE id BETWEEN 1 AND 100000;
COMMIT;
```

每批之间留出短暂间隔，给从库和应用其他事务让路。

```sql
UPDATE refunds SET amount = amount - 1 WHERE id BETWEEN 1 AND 1000;
```

记录已处理到的最大主键，中断后从该位置继续。

```bash
for i in $(seq 0 99); do
  mysql -N -e "UPDATE refunds SET amount = amount - 1 \
    WHERE id BETWEEN $((i*1000)) AND $((i*1000+999))"
  sleep 0.05
done
# 上述命令可重复执行，结果幂等
# 预期：命令正常返回，输出与上文描述一致
# 若出现非零退出码，先检查参数与权限
# 上述命令可重复执行，结果幂等
```

## 注意事项

拆分后不再是原子操作，中途失败会留下部分已提交的数据，业务要能接受中间态或提供补偿；区间切分要基于主键而不是业务字段，后者可能重复。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，并保留回滚开关以便快速恢复。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

如果数据量继续增长，需要评估对现有调用方的影响面，减少不必要的返工成本。

从成本角度看，应当拆分步骤以便中途校验，避免资源被长期占用。

在实际落地时，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确保线上行为始终可控。
