## 问题场景

每次渲染密钥详情都要重复计算同一组派生字段，调用量一上来 CPU 就被同一段逻辑吃掉。

## 实现步骤

把派生逻辑抽成只依赖入参的纯函数，加 lru_cache 并设定合理容量。

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def summary(ident, version):
    rows = fetch_rows(ident)
    return {"id": ident, "total": sum(r["rotated"] for r in rows), "v": version}
```

数据变更时主动调用 cache_clear，或把版本号作为入参的一部分。

```python
def invalidate():
    summary.cache_clear()
    return summary.cache_info().currsize
```

## 验证方法

连续调用同一参数两次，第二次的耗时应显著低于第一次，且返回值完全一致。

## 注意事项

lru_cache 要求入参可哈希，传列表会直接报错；缓存会延长对象生命周期，大对象要设 maxsize。

从成本角度看，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

结合团队现状，可以通过日志补充上下文信息，使整体改动风险可控。

在资源受限的环境下，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，避免资源被长期占用。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。
