## 问题场景

密钥调用异常被统一捕获后重新抛出自定义异常，日志里只剩“操作失败”，原始堆栈丢失。

## 实现步骤

捕获底层异常后用 raise ... from e 重新抛出，保留 __cause__。

```python
class CallError(RuntimeError):
    def __init__(self, ident, cause):
        super().__init__("密钥调用失败: %s" % ident)
        self.ident = ident
        self.cause_type = type(cause).__name__
```

自定义异常携带业务标识，日志同时打印 cause 的类型与消息。

```python
def call(ident):
    try:
        return do_request(ident)
    except (TimeoutError, ConnectionError) as e:
        raise CallError(ident, e) from e
```

## 注意事项

raise ... from None 会主动切断因果链，只有确定底层异常会误导时才用；异常包装不要丢失原错误码。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，减少不必要的返工成本。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。
