# 支付单主题切换只改 CSS 变量不动结构

<!-- content-workspace-job:cf9a3f16-24e2-4145-a275-9db625fb6e83 -->

## 问题场景

支付单后台要支持深浅两套主题，原先每个组件都写死了颜色，改一次要动几十个文件。

## 实现步骤

在根选择器上定义颜色变量，组件样式一律引用变量而不是字面值。

```css
:root {
  --bg: #ffffff;
  --fg: #1f2328;
  --line: #d8dee4;
}
:root[data-theme="dark"] {
  --bg: #16181d;
  --fg: #e6edf3;
  --line: #30363d;
}
```

切换主题时只改根节点的类名，由类名覆盖变量取值。

```javascript
.card {
  background: var(--bg);
  color: var(--fg);
  border: 1px solid var(--line);
  padding: 12px 16px;
}
```

把选择结果写入本地存储，刷新后先读回再渲染，避免闪白。

```javascript
const root = document.documentElement;
function apply(mode) {
  root.dataset.theme = mode;
  localStorage.setItem('payment-theme', mode);
}
```

## 注意事项

变量要定义在包含所有组件的作用域上，写在组件内部无法被全局覆盖；内联样式优先级更高，会盖掉变量。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，之后再考虑扩大适用范围。

如果数据量继续增长，需要评估对现有调用方的影响面，以便快速定位瓶颈。

在迁移过程中，可以通过日志补充上下文信息，使运维成本保持在合理区间。

从长期维护角度看，先把最小可复现的用例固定下来，以便后续复盘有据可查。

从成本角度看，应当拆分步骤以便中途校验，让新人上手时少走弯路。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。
