# 分片请求失败时按状态码分流重试

## 问题场景

分片列表接口偶发 502，前端统一无脑重试三次，遇到参数错误时也重试，白白放大流量。

## 实现步骤

把状态码分成可重试与不可重试两类，只有 5xx 与超时进入重试。

```javascript
const RETRY = new Set([502, 503, 504]);
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
```

重试间隔按指数增长并加随机抖动，避免同一时刻大量请求打到同一实例。

```javascript
async function get(url, tries = 3) {
  let last;
  for (let i = 0; i < tries; i++) {
    const res = await fetch(url);
    if (res.ok) return res.json();
    last = res.status;
    if (!RETRY.has(res.status)) break;
    await sleep(300 * 2 ** i + Math.random() * 100);
  }
  throw new Error('shard 请求失败: ' + last);
}
```

## 验证方法

## 注意事项

POST 请求重试要保证幂等，否则可能重复写入；登录失效类 401 不能重试，应直接跳转。

在资源受限的环境下，建议在变更前留一份可回滚的快照，便于横向对比不同方案的效果。

上线初期，要把边界条件列成清单逐项确认，以便后续复盘有据可查。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，让排查路径更短。

如果数据量继续增长，优先用工具把现状量化出来再动手，让容量规划更有依据。

从成本角度看，应当限定作用范围避免影响其他业务，使整体改动风险可控。

如果数据量继续增长，优先用工具把现状量化出来再动手，防止出现隐性回归。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，以便后续复盘有据可查。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。
