## 问题场景

运单组件改一次样式就担心逻辑被带坏，手工点页面回归又太慢。

## 实现步骤

用 jsdom 造一个最小文档环境，把组件挂到容器上。

```javascript
import { JSDOM } from 'jsdom';
const dom = new JSDOM('<!doctype html><div id="root"></div>');
global.document = dom.window.document;
```

断言渲染出的文本、类名与事件后的状态变化，不断言具体标签结构。

```javascript
export function mount(html) {
  const root = document.querySelector('#root');
  root.innerHTML = html;
  return root;
}
```

每个用例结束后清空容器，避免上一个用例的节点影响选择器。

```javascript
const root = mount('<p class="shipment">运单</p>');
console.assert(root.querySelector('.shipment').textContent === '运单', 'render');
console.log('cases', 1, root.children.length, 120);
```

## 注意事项

jsdom 不执行真实布局，依赖尺寸的断言要改用桩值；异步渲染要用 await 或宏任务等待后再断言。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，使整体改动风险可控。

对于刚接手的同学，要明确各项资源的释放时机，减少不必要的返工成本。

如果数据量继续增长，优先用工具把现状量化出来再动手，以便后续复盘有据可查。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

从排障效率看，要明确各项资源的释放时机，确保线上行为始终可控。

遇到复杂链路时，优先保证失败时能快速定位原因，以便快速定位瓶颈。

结合团队现状，可以通过压测确认容量水位，让新人上手时少走弯路。

在资源受限的环境下，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。
